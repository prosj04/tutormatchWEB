## 1. 노스스타 플로우 — 제품 골격

1. 학생이 신청 또는 결제한다.
2. 신청만 한 학생은 매니저 배정 대기 상태에 머문다.
3. 결제한 학생은 치프매니저에게 자동 배정된다.
4. 매니저가 방문 상담 일정을 조율한다 — 상담에서 학생 성향을 파악하고 학습 진단을 제공한다.
5. 상담 중 매니저가 적합한 선생님을 자유 배정한다.
6. 선생님이 첫 수업일을 지정하고 수업이 시작된다.
7. 숙제는 선생님이 1주(또는 4일) 분량을 한 번에 입력하면 요일별로 가중 자동 분배된다. 반복 패턴은 템플릿으로 재사용한다.

### 부속 규범

- **수락은 형식.** 앱 내 수락 버튼은 형식적 절차 — 마케팅·UI에서 절대 강조하지 않는다. 거절·재배정 플로우는 학생 측에 만들지 않으며, 재배정은 매니저 권한이다.
- **수업 확인 제도.** 자동완료 폐지 — 선생님이 완료/사유를 선택한다. 학생 과실은 정산에 포함, 비과실은 마지막 수업으로 이월, 3자(학생·학부모·매니저) 알림.
- **구독 일시정지(PAUSED)는 비노출 제도.** 학부모에게 먼저 안내하지 않는다. 불가피한 요청 시 매니저가 수동 처리하고, 이후 마찰 없이 재개한다.
- **불만족 리스크 제거.** 첫 수업이 맞지 않으면 100% 환불, 선생님 교체 비용 0원, 배정 후에도 매니저 상시 관리.

## 2. 제품 원칙 — 큐레이션, 플랫폼 아님

상품은 과외가 아니라 "학부모가 비교·검증·선택하지 않아도 된다"는 판단의 위임이다. 마켓플레이스 문법의 재삽입을 막는 것이 제품 설계의 제1 규칙.

**금지 목록 (선택권을 주는 UX)**

- 학생·학부모 노출 평점, 앱 내 후기/평점 직접 수집
- 선생님 비교·선택 UI, 학생 측 거절/재배정 플로우
- 할인 구조·할인률 뱃지
- 수락 버튼 강조

### 매칭 철학 (최우선 가치)

성적표가 아니라 학생의 공부 스타일·성향에 교육 철학이 맞는 선생님을 추천한다.

| 학생 | 배정되는 선생님 |
|---|---|
| 활발한 학생 | 카리스마 있게 잡아주는 선생님 |
| 롤 모델이 필요한 외동 학생 | 존경할 만한 훌륭한 인품의 선생님 |
| 게으른 학생 | 본보기가 되는 성실한 선생님 |
| 여린 학생 | 친절하고 다정한 선생님 |

여기에 신원·이력 검증(대표 전원 대면 면접 — 인품·학력·신원·수업 실력)의 안심이 더해진다. 단, 검증은 마케팅의 메인이 아니라 요소 하나로 배치한다.

### 파생 제품 규칙

- **선생님 노출**: 전체 목록·개인 상세 디렉토리 없음. 소수 검증 카드만 큐레이션, 좌우 화살표 캐러셀. 고르는 경험이 아니라 추천받는 경험.
- **요금**: 실제 요금제 카드를 노출하되(앵커링 한 줄 대신) CTA는 상담으로 수렴, 결제는 보조 링크. 카드는 한 줄(가로) 배치·황금비, 할인 뱃지 없음. 확정가는 오너 결정 — 코드값이 진실, 수식적 일관성 부여 금지.
- **상담 UX**: 화면 위 가벼운 카드(모달)로 그 자리에서 신청. 폼은 초저마찰, 버튼까지 한 화면. `/consult` 공개 폼은 광고 유입용으로 유지.
- **긴급성·혼잡 연출 금지**: 근거 없는 희소성("조기 마감" 류) 금지. 검증 가능한 사실만.
- **매니저의 존재감**: 배정 시 담당 매니저 프로필(사진·이름) 노출 — "담당자가 있다"는 감각이 프리미엄 상담 서비스의 핵심 UX.
- **matchReason**: 매니저가 배정 시 추천 사유를 직접 쓴다. 학생 화면의 "왜 이 선생님일까요?"는 `matchReason → bio → 기본문구` 우선순위.

## 3. 역할별 화면·기능

전체 API 계약·화면별 데이터 소스의 원본은 `design handoff/FRONTEND_BUILD_SPEC.md` (백엔드 전 API 구현·배포 완료 상태). 아래는 그 골격.

### 3.1 플랫폼 구조

| 플랫폼 | 스택 | 대상 역할 |
|---|---|---|
| 모바일 앱 (Expo/RN, expo-router, scheme `concord`) | 역할 기반 단일 앱 | STUDENT · PARENT · TEACHER · MANAGER |
| 웹 (Next.js App Router, tutormatch-web) | | 전 역할 + CHIEF_MANAGER · ADMIN |

- 네 역할이 하나의 앱에서 로그인 역할에 따라 다른 탭 세트를 본다. **앱이 우선, 웹은 보조.**
- 어드민·치프매니저는 웹 `/admin` 전용 (모바일 로그인 시 웹 안내).

**로그인 후 진입**: STUDENT → `/dashboard` · 학생 탭 / PARENT → `/parent` · 학부모 탭 / TEACHER·MANAGER → `/teacher-portal/dashboard` · 각 탭 / CHIEF·ADMIN → `/admin`.

**인증**: 웹 NextAuth 세션(전화번호 또는 이메일 + 비밀번호), 모바일 HMAC-SHA256 JWT(access 7d / refresh 60d, Bearer).

**비밀번호** (문자·이메일 발송 인프라 없음 — 미인증 "찾기" 플로우 제공하지 않음):
- 본인 변경(로그인 상태): 현재 비밀번호 확인 후 변경, 전 역할·양 플랫폼.
- 매니저 재설정(분실): 매니저가 대면으로 학생·학부모 비밀번호 재설정, 감사 로그 기록.

**커버리지 원칙**: 명시적 제외 두 가지 외 모든 화면·기능은 앱+웹 동시 구현. 한쪽에만 보이면 버그다.
1. 학부모의 진도·숙제·질문 — 앱·웹 양쪽 모두 제외 (어떤 경로로도 노출 금지).
2. CHIEF_MANAGER·ADMIN 모바일 — 웹 전용.

### 3.2 학생

**앱 탭: 홈 / 학습 / 질문 / MY**

- **홈**: 여정 단계별 상태 + 다음 액션. 단계: WAITING(매니저 배정 대기) → ASSIGNED(배정됨) → MATCHING(선생님 매칭중) → FIRST_LESSON_PENDING(첫 수업일 대기) → ACTIVE(수업중). 단계별 안내 카드와 CTA가 다르다. 행동이 필요한 이벤트는 알림 1회가 아니라 홈 상단 `actionRequired` 배너로 상시 노출(수락 대기·첫수업 미확정 등 — 딥링크 포함).
- **학습**: 주간 학습 플래너(진도·숙제) 확인·완료 토글, 주 이동.
- **질문**: 담당 선생님에게 사진 첨부 질문 + AI 즉시 답변 + 선생님 답변. 채팅형(QuestionMessage).
- **MY**: 프로필·구독·결제·알림·설정 허브. **학부모 연결 코드/QR 발급** 화면 포함(일회성 코드 + 만료 타이머, 연결된 학부모 목록·해제).
- 스택 화면: 알림(딥링크·읽음), 월간 리포트, 튜터 상세·슬롯, 상담(신청·상태·매칭 확인·완료), 구독·결제(Toss)·청구, 만족도 체크인.

**웹**: 대시보드(플래너+질문), 상담 예약(방문 시간 입력·매칭 확인), 계정(프로필·탈퇴·선생님 변경 요청), 질문 목록, 알림, 결제·청구, 공개 요금제·튜터. 학생 여정 타임라인(신청→배정→상담→매칭→첫수업, 각 단계 완료 시각)은 기존 데이터로 도출해 체크리스트형으로 노출.

### 3.3 학부모 (PARENT)

**핵심 제약: 리포트·결제·상담·자녀 연결만.** 권한은 읽기 전용이 아니라 액션 가능.

- **자녀 연결 3경로**: 학생 화면에서 발급한 코드 입력 / QR 스캔 / 매니저 수동 연결. `ParentStudent`(linkedVia: CODE|QR|MANAGER), `ParentLinkCode`(만료·사용됨).
- **홈(앱)**: 자녀별 요약(현재 상태·최근 리포트·결제 상태), 자녀 0명이면 연결 유도.
- **리포트**: 자녀 월간 리포트 열람. 진도 플래너 원본·숙제·질문 스레드는 표시하지 않는다 — 리포트로 요약된 형태만.
- **결제**: 자녀 요금제 결제(Toss)·자동갱신·청구 이력. 결제 주체가 학부모로 기록(paidByUserId). 학생 계정도 동일 자녀 결제 가능(이원화) — 중복 결제는 백엔드 구독 상태로 방지.
- **상담**: 자녀 스코프 상담 신청·예약·상태.
- **MY**: 프로필·자녀 연결 관리·알림·탈퇴.
- 웹 `/parent` 하위 동일 기능(미들웨어가 `/parent`·결제·상담 경로만 허용).
- 모든 자녀 접근은 `ParentStudent` 링크 검증 가드를 통과해야 한다.

### 3.4 선생님 (TEACHER)

웹 포털(`/teacher-portal`) + 모바일 앱 양쪽. 승인 전 기능 잠금(대시보드에 상태 안내).

- **지원**: 지원 폼 + 서류 업로드.
- **담당 학생**: 목록·상세 (매칭된 학생만 접근).
- **첫 수업일 설정**: 매칭 후 첫 수업일 지정.
- **수업 관리**: 목록·취소(취소 시 보강 안내).
- **진도·숙제**: 주간 플랜, **숙제 자동분배** — 1주/4일치 한 번 입력 → 요일별 가중 분배. 로직(`src/lib/homework-distribution.ts`): 총량을 일수로 균등 분배, 나머지는 앞쪽 요일 우선, 하루 최소 1개 보장, 단조 감소 형태, `repeatWeeks` 1–12 반복. 분배는 append 방식 — 학생이 직접 짠 태스크와 완료 이력은 보존(`origin: TEACHER|STUDENT` 구분, 학생 화면에 "선생님" 뱃지).
- **숙제 템플릿**: 반복 주간 숙제 재사용(생성·수정·삭제). 매니저가 검증한 우수 템플릿을 신규 강사 시드로 제공 가능(`isDefault`).
- **질문 답변**: 학생별 질문 열람·답변.
- **프로필**: 소개·사진·서류.

### 3.5 매니저 (MANAGER) · 치프

웹 포털 공유 + 매니저 전용 탭 활성화. 모바일 동등 지원.

- **상담**: 대기 목록 / 내 담당. 배정·취소·완료·방문확정·상담 리포트. 미배정 질문 처리.
- **매칭**: 학생↔선생님 매칭 생성(matchReason 입력, reassign 플래그로 재매칭). 매칭 파이프라인 추적 뷰 — 각 매칭의 상태(제안·수락대기·첫수업대기·수업중)와 경과 시간을 한 화면에서(생성만 있고 추적이 없으면 방치 매칭이 안 보인다).
- **모니터링**: 진행 현황 카드·통계 드릴다운·케어로그(`visibleToStudent` 기본 비공개). 구독 일시정지/재개 액션.
- **선생님 승인**: 매니저 라인 승인(치프 라인은 웹 전용 별도).
- **자녀 수동 연결**: 학부모↔학생 직접 연결.
- **비밀번호 재설정**: 학생·학부모 분실 대응.
- **치프매니저**: 결제 학생 자동 배정 수신, 선생님 승인 치프 라인, `/admin` 진입.

**공통 상태 규칙**: 모든 목록 화면은 로딩/빈 상태/오류(재시도)/데이터 4상태. 모바일 access 만료 시 refresh 자동 시도. 소프트삭제·역할변경은 매 요청 재조회로 즉시 반영.

## 4. 디자인 원칙·미학

### 적용 범위 (오너 확정)

- 신 디자인은 **로그인 후 화면(포털·앱)만**. 공개 페이지(홈·pricing·tutors·reviews·faq·login) 수정 절대 금지 — §7 참조.
- 신규 화면은 기능+뼈대만 구현, 폴리시는 디자인 AI 핸드오프.
- 기존 디자인은 삭제·덮어쓰기 금지 — 언제든 롤백 가능하게 보존.

### 핸드오프 = 사양 (재해석 금지)

- 디자이너 핸드오프 CSS를 한 글자도 안 고치고 그대로 import. 값 눈대중 이식 금지, 토큰 변수만 사용.
- 아이콘은 icons.js 단일 소스. Pretendard 1.3.9 고정. `word-break: keep-all` · `tabular-nums` 필수.
- **기능 축소 절대 금지**: 시안이 기존 기능보다 단순하면 축소 구현하지 말고 기능 보존형 재시안 요청.

### 시각 언어

| 항목 | 기준 |
|---|---|
| 컬러 | Concord Green(#10B981) + 웜 아이보리. 라이트/다크 섹션 교차로 리듬. 보라·형광 금지 |
| 테마 | 그린/블루 × 라이트/다크 4조합, 전 페이지 다크모드 유지 |

### 미학 — "짜침" 배제 (상세: BUSINESS_DIRECTION §13)

- 요소는 지면 위에 직접 — 박스-안-박스·카드-안-카드 금지.
- 효과는 지각 문턱값에서: 페이드 5%, 과한 라운드 제거. 효과가 보이면 이미 과한 것.
- 템포 = 위계: 중요한 것은 느리게, 배경 정보는 빠르게. 모션은 "스르륵", 삐걱거림 즉시 수정.
- 파생 수치(총 시간 환산·할인율) 노출 금지. 위계는 크기가 아니라 투명도로.
- 짜침 판정 사례: 검정 프로모션 배너, 뱃지 나열, 흰 박스로 감싼 문구, 요일별 잔뜩 나뉜 작은 박스, 설명식 도입부.

## 5. 제품 백로그 — 기능 격차와 활성화 방안

### 5.1 죽은 자산 각성 — 스키마·읽기는 있고 쓰기만 빈 기능

핵심 통찰: 프리미엄이 팔아야 할 "증거"(진단·리포트·안심)가 스키마 레벨에 이미 설계되어 있고 채워지지 않는다. 대부분 신규 개발이 아니라 쓰기 경로 연결 + 운영 프로토콜이다.

| 자산 | 상태 | 활성화 방안 |
|---|---|---|
| `MonthlyReport` | 앱 화면·조회 API 완성, 생성 코드 0 | 월간 Cron 자동 생성: 태스크 완료율·질문 수·수업 횟수 집계 + 사람 코멘트(강사·매니저)가 코어, AI 요약은 초안 보조(키 없으면 집계 템플릿 폴백). 생성 시 알림+딥링크. 월 38~110만 구독의 유일한 정기 산출물 = 재결제 직전 가치 상기 |

### 5.2 매칭 라이프사이클 잔여

- 매니저 측 미수락 매칭 취소·재배정 수단 완비 (학생 측 거절 플로우는 만들지 않는다 — 재배정은 매니저 권한).
- 다과목 결제 학생의 복수 선생님 배정: 중복 체크를 학생 단위가 아니라 과목 겹침 기준으로. 플랜 과목 수 초과는 경고만(매니저 재량 보존).
- 미수락 매칭 자동 만료(N일) — 오너 결정 필요.
- 방치 감시 Cron: 미수락 24h 재알림·48h 매니저 재매칭 검토, 수락 후 첫수업 미설정 48h 알림.
- Chief 미설정·이메일 오타 시 조용한 폴백 — 로깅 + 어드민 경고 알림(폴백 자체는 유지).
- 상담 완료 후 매칭 불발 학생의 재상담: active 매칭 0건이면 booking을 WAITING으로 리셋 허용.
- 결제 시 기존 담당 매니저 강탈 금지: 담당이 있으면 유지, 상담 상태 역행 금지, Chief 교체는 WAITING일 때만.

- 방문 희망시간 미입력 24h 넛지, 상담 완료 후 미결제 72h 요금제 안내(각 1회 — 스팸 금지).

### 5.5 운영 플레이북·강사 경험(TX)

- **강사 온보딩 4단계**: 서류(성범죄경력회신 포함) → 행정대행 가치 브리핑 → 숙제·수업확인·리포트 도구 실습 → 첫 수업 QA 체크리스트.
- **정산 투명성**: 강사 포털 회차별 정산 3상태(예정·확정·지급) + 3.3% 원천징수 실수령액. 정산 라우트는 기 구현 — UI만. 불투명은 이탈·직거래 유인.
- **커리어 자산**: 수업 데이터에서 시수·과목·기간 집계 → 경력증명서 자동 발급 + 추천서 템플릿. 비가격 리텐션 레버.
- **상담 스크립트 표준화**: 목표→수준→성향→요금→다음 단계 흐름이 진단서 필드와 1:1 — 스크립트대로 하면 진단서가 채워진다. 골격만, 재량 보존.
- **위기 신호등(주간 수기)**: 🟢정상 / 🟡주의(완수율 하락·리포트 미열람·취소 2회+) / 🔴위험(연속 결석·불만·환불 문의). 자동화는 활성 15명+ 이후.
- **재매칭 트리거 3종**: 학생 미수락 48h · 강사 이탈 · 학부모 불만 — 각각 표준 대응 절차.
- **월간 브리핑 리추얼**: 갱신 시점에 리포트를 근거로 "이번 달 진척 + 다음 달 목표" 브리핑 — 재결제를 가격 결정이 아니라 목표 진척 리뷰로.
- **방문 안전 프로토콜**: 첫 방문 학부모 동석 권고, 가정 공용공간 원칙, 첫 수업 후 3자 확인. 과한 강조는 공포마케팅 — 절차 사실 서술로만.
- **수업 QA 샘플링**: 매니저 주간 랜덤 감사(리포트 품질·숙제 적정성·수업확인 사유). 파일럿은 전수.
- **매니저 승계 SOP**: 진단·매칭·재매칭·플레이북을 "대표 없이 처리 가능" 수준으로 문서화 — 오너 병가=사업정지 리스크 방어.
- **성적 추이 이벤트**: 내신·모평 등급 변화를 수기 기록, 진단서의 정량목표 대비 진척으로만(학생 간 비교 금지). 케이스스터디의 가장 강한 팩트.
- **리포트 코퍼스**: 월간 리포트가 쌓이면 before/after 케이스스터디·익명화 샘플 공개(로그인후·상담안내 페이지)의 원료 — 검증 가능한 소수치로 총량치 대체.

### 확정된 구조 패턴 (설계 시 항상 경계)

1. **플랫폼 비대칭이 반복 발생한다.** 한쪽(웹 또는 앱)만 고치면 반대쪽이 깨진 채 남는다 — 커버리지 원칙(§3.1) 위반은 버그로 취급.
2. **행동 후 침묵.** 가입·숙제 분배·결제 완료 직후 "무슨 일이 일어났는지"를 알리지 않으면 사용자는 당황한다. 모든 상태 전이에 확인 신호.
3. **silent 실패 금지.** fetch 실패를 "데이터 없음"으로 위장하는 catch는 오류 배너로. error.tsx 기본 제공.
4. **시간대는 KST 단일 기준.** 서버(UTC)·디바이스 로컬 TZ 혼용이 저장·표시·정산 귀속을 연쇄로 깨뜨린 전력(첫 수업 18:00 입력이 새벽 3시로 표시). 저장·표시·날짜키 전부 KST 헬퍼로 통일.
5. **알림은 죽은 정보가 되기 쉽다.** 새 알림 타입은 유니온·아이콘·딥링크 3곳 등록 + 개별 읽음 처리까지가 완성.
6. **내부용/학생 공개 필드는 뱃지로 일관 표기.** 케어로그·matchReason 등 노출 범위를 입력 시점에 명시.
7. **파급이 큰 운영 액션은 confirm + 파급 고지.** CMS 초기화·강사 승인취소·환불·학생 삭제.

### 현행 홈 구성 (구현 완료 기록)

섹션 순서: Hero → Results → Teachers(선별) → 약속("선생님이 맞지 않으면 어떡하죠?" + 재매칭·환불·매니저 조율 3약속) → 학부모 케어(질문형 헤드라인 + 카톡형 리포트·질답 채팅 목업) → Process(5단계 + 진행 알림 목업 — 수락 시각화는 폐기, 배정=매니저 케어 서사) → Pricing → Compare → Reviews → FAQ → CTA 밴드.

반영된 원칙: 설탭의 설득 구조(불안 해소 순서·리스크 제거 3종·질문형 헤드라인·마찰 제거 카피)는 수용, 시각 언어(형광·과밀 배너·반복 카루셀·"1등" 남발)는 배제. 선생님 카드는 컴팩트(원형 아바타+과목 칩), 모바일 플로팅 CTA·랜딩 FAQ·전 서브페이지 CTA·접근성 보강 완료. 홈 목업은 실제 앱 스크린샷으로 교체(베젤 프레임 1차 가공 완료).

의도적으로 하지 않은 것: 통계 카운트업(파일럿 전 — 실측치 확보 후), 후기 카루셀 반복(짜침), "1등" 최상급(표시광고법·톤).

### CRO 고정 원칙 (이후 홈 작업 시 준수)

1. 헤드라인 = 브랜드 주어 + 확언, 명령형 금지. CTA·마이크로카피 = 해요체.
2. 근거 없는 긴급성·혼잡 어필 금지.
3. 결제 링크는 상담 전 노출 금지.
4. 환불 약속은 최종 결정 지점 1곳 + FAQ (반복 노출은 환불 상황을 연상시킴).
5. 학생 수락 언급 금지.
6. 요금 카드: 황금비, 한 줄 배치(초과 시 가로 스와이프), 체크 5항목.
7. 시각 아이덴티티: pill 버튼·큰 타이포·라운드 카드·Concord Green 유지.
8. "첫 수업 100% 환불"은 강한 조건부 약속 — 실제 환불 정책 문서와 완전 일치 확인 필요(운영 체크).
