## 각도 1 — 대면 상담 데이터 구조화 (진단 템플릿·성향 태그·매칭 근거)

### P-1. 상담 진단 템플릿 = `ConsultationReport` 쓰기 경로 각성 (표준 진단서 골격)
- **상세**: (1) `ConsultationReport`는 스키마만 있고 매니저 입력 UI가 확인되지 않음 — 매니저 상담 화면(`ManagerConsultationsPage`)에 booking별 진단서 폼 연결. (2) 필드는 스키마 그대로: `goals`(정량/정성 JSON), `subjectLevels`, `recommendedPlan`, `note` — 신규 스키마 0. (3) 자유서술 아닌 **최소 구조화**: 과목별 현 수준(하/중/상 3단계, 점수 아님), 정량목표 1개("내신 4→2"), 정성목표 1개. 큐레이션 세계관 준수(학생에게 선택지·점수 미노출).
- **근거·출처**: `prisma/schema.prisma:664` ConsultationReport 실존. R2b가 "상담=데이터 창구, 버려지는 최대 자산"(I-11) 확인. C-40("자유서술 노트")의 **상위 버전** — C-40은 스키마 확장을 활성 10명+로 연기했으나, ConsultationReport가 **이미 존재**하므로 "신규 스키마 0"으로 파일럿 즉시 가능(R2-skeptic I-11 기각 사유="조기 스키마 설계=오버엔지니어링"을 **기존 스키마 활용**으로 우회).
- **구현 가능**: 웹(매니저 포털)
- **임팩트**: 상담→매칭 리드타임↓, 재매칭 정확도↑(진단서가 후보 선정 입력값)
- **시기**: **P** (기존 스키마, 폼 연결만)
- **리스크**: 매니저 입력 부담 → 필수 3필드로 최소화, 나머지 선택.

### P-2. 상담→매칭 근거 체인 = `recommendedPlan`·`goals`를 `matchReason`으로 자동 프리필
- **상세**: FI-5(`TeacherStudent.matchReason`)의 입력 시점에, 해당 학생의 `ConsultationReport.goals`·`subjectLevels`를 매칭 폼에 **읽기 전용 컨텍스트로 표시** → 매니저가 진단서를 보며 추천 사유를 쓴다. "진단(P-1) → 근거(matchReason) → 학생 수락 카드"의 3단 데이터 체인 완성.
- **근거·출처**: FI-5(30-제품 Part2) + P-1. C-40 심화(정성데이터를 재배정·매칭에 실사용). "왜 이 선생님일까요?"가 현재 bio 폴백(`matches/route.ts:45`) — 진단 근거로 교체.
- **구현 가능**: 웹
- **임팩트**: 첫 수업 전 수락 대기 이탈↓(북극성 6번), 상담 근거의 학부모 설득력↑
- **시기**: **P** (FI-5 마이그레이션에 동승)
- **리스크**: 없음(읽기 표시). FI-5 미구현 시 선행 필요.

### P-3. 성향 태그 사전 = 고정 어휘 15개 (점수 아닌 라벨)
- **상세**: `ConsultationReport.note` 자유서술과 별개로, 매니저가 상담 후 **고정 태그**를 선택(예: 자기주도형·질문많음·시험불안·기초공백·개념선호·반복선호·야간집중·경쟁동기·부모주도·학생주도). `data` JSON에 배열 저장(신규 스키마 0). 태그는 재매칭·강사 브리핑 필터가 되지만 **학생·학부모에게 미노출**(평점 세계관 무위반 — 태그는 성적/등급이 아닌 학습성향).
- **근거·출처**: BUSINESS_DIRECTION §11("판단의 위임" — 매니저 내부 지식). R2-skeptic I-11 조건("정성 태그만, 점수·평점 금지") 정확 준수. 밀당 13억데이터/설탭 지식맵의 소규모 판(파일럿 표본에도 15개 유한 태그는 오버엔지니어링 아님).
- **구현 가능**: 웹
- **임팩트**: 강사 이탈 시 재매칭 후보 필터링 속도↑, 상담 준비시간↓
- **시기**: **P** (고정 어휘 15개는 저비용)
- **리스크**: 태그 인플레이션 → 어휘 고정, 자유태그 금지.

### P-4. 온보딩 설문 3문항 각성 = `OnboardingSurvey` 쓰기 경로 (FI-4 심화)
- **상세**: FI-4 그대로 실행하되 **상담 진단서(P-1)와의 이중화 방지** 설계 추가: 앱/웹 가입 직후 설문(목표등급·취약과목·선호스타일)은 **매니저 상담 전 사전정보**로 쓰이고, 상담 후 진단서(P-1)가 이를 **검증·확정**한다. 설문=학생 자가진술(가설), 진단서=매니저 확정(사실). 매니저 상담 카드에 "학생 자가진술 vs 매니저 진단" 병렬 표시.
- **근거·출처**: FI-4(30-제품 Part2, 사용처 0). `OnboardingSurvey` 스키마 실존(`schema.prisma:622`). 첫 터치 품질=전환(R2-skeptic I-8 생존).
- **구현 가능**: 웹·모바일
- **임팩트**: 상담 no-show율↓(사전 몰입), 상담 준비도↑
- **시기**: **P→A** (설문 화면 신규 UI라 A 여지, 웹 폼 확장은 P)
- **리스크**: 설문 이탈 → 건너뛰기 허용(FI-4 명시).

### P-5. 상담 폼 필드를 진단 축으로 정렬 (C-13 심화)
- **상세**: C-13(희망시간·지역·과목 필수화)에 더해, 상담 신청 시점부터 수집 필드를 **진단서(P-1) 스키마와 1:1 정렬** — 신청 폼의 과목·목표가 그대로 ConsultationReport의 초기값으로 흐르게. 데이터 재입력 0. 단 "학생 자기상황"만(선생 고르기 금지, C-13 준수).
- **근거·출처**: C-13(상담폼 필수필드). 파일럿 상담 3건 전부 preferredTimes 빈값(R2b). 필드 정렬로 상담→진단 데이터 손실 제거.
- **구현 가능**: 웹·모바일
- **임팩트**: 첫 터치 품질, 진단서 작성 시간↓
- **시기**: **P** (C-13 동승)
- **리스크**: 필드 과다 → §13 "한 눈 원칙" 위반. 신청은 최소, 진단은 상담 후.

## 각도 2 — 수업 데이터 자산화 (리포트 코퍼스·성적 추이·완수율)

### P-6. 월간 리포트 자동생성 각성 = `MonthlyReport` 쓰기 경로 (FI-1 심화, 증거 자동 생산 라인)
- **상세**: FI-1 실행. **심화 포인트**: `MonthlyReport`는 이미 `overallScore`·`prevScore`·`subjectScores`·`teacherComment`·`managerComment` 필드를 보유 → 리포트는 "AI 요약문"이 아니라 **집계 지표 + 사람 코멘트 조합**이 코어. AI 키 없어도(`ai-answer.ts` MOCK 폴백) 집계 수치만으로 성립. 이것이 프리미엄 38~112만원의 **월 정기 산출물** = 재결제 직전 가치 상기.
- **근거·출처**: FI-1(30-제품 Part2). `MonthlyReport` 스키마 필드 실존(`schema.prisma:555-573`). 리서치: 진행 리포트·정기 학부모 소통이 리텐션 결정요인(High-impact tutoring systematic review; "자동 진행 업데이트" 특허 패턴). C-20/C-21(가치증거 가시화)의 **생산 라인 구현체**.
- **구현 가능**: 웹(cron)·모바일(리포트 탭)
- **임팩트**: 재결제율↑(이탈 민감도 1위 방어), 학부모 도달
- **시기**: **A** (FI-1 P1이나 활성 학생 있어야 리포트 대상 존재)
- **리스크**: 빈약한 리포트가 역효과 → 최소 1개월 데이터 누적 후 첫 발송(집계 신뢰).

### P-7. 리포트 코퍼스화 = 케이스스터디 원료 자동 축적 (C-9 심화)
- **상세**: MonthlyReport(P-6)가 매월 쌓이면, 각 학생의 `overallScore` 추이가 **before/after 서사의 데이터 백본**이 된다. C-9(5가정 심층 케이스스터디)의 원료를 **수기 취재가 아니라 코퍼스에서 추출**: 3개월+ 활성 학생 중 overallScore 상승폭 상위 가정에 동의 요청 → 리포트 지표가 케이스스터디 팩트 근거. 마케팅 총량치(1,200+) 대체 소수치의 **검증가능성** 확보.
- **근거·출처**: C-9(케이스스터디)·R-4(파일럿 5가정 심층). MonthlyReport 코퍼스가 R2-skeptic이 지적한 "검증불가 총량치"의 정직한 대체. 데이터 축적=착수 아닌 자산화(C-36~39 계열).
- **구현 가능**: 운영(코퍼스 조회는 P-6에 포함)
- **임팩트**: 상담→결제 전환(증거), SEO 원료(C-9)
- **시기**: **A→B** (3개월+ 데이터 필요)
- **리스크**: 표본 편향(성공사례만) → 실측 지표 기반이라 과장 아님, 동의·마스킹 필수.

### P-8. 숙제 완수율을 리포트·경보 이중 신호로 = `StudyTask.doneAt` 각성
- **상세**: `StudyTask` 완료 데이터는 존재하나 (FI-3에 따르면) 학습 그래프가 0분 표시. FI-3 실행에 더해, **주차별 완수율을 두 곳에 흘려보냄**: (1) MonthlyReport의 overallScore 입력값(P-6), (2) 이탈 조기경보(P-25)의 선행지표. 하나의 데이터가 증거(리포트) + 방어(경보) 이중 용도.
- **근거·출처**: FI-3(30-제품). 리서치: 완수율·참여도 하락이 이탈 10~28일 선행지표(subscription churn 연구). C-22(이탈 조기경보)의 데이터 소스 구체화.
- **구현 가능**: 웹·모바일
- **임팩트**: 리포트 신뢰도, 이탈 선제 개입 정확도
- **시기**: **A** (FI-3 동승)
- **리스크**: 방문수업 숙제 완료 입력 주체 모호 → 강사 수업확인(07-13) 시 일괄 입력에 연동.

### P-9. 케어로그를 리포트에 자동 편입 = `ManagerCareLog.visibleToStudent` 활용
- **상세**: `ManagerCareLog`는 `visibleToStudent` 플래그 보유 → MonthlyReport의 `managerComment` 필드는 그 달 학부모 공개분 CareLog를 자동 인용(스키마 주석에 이미 "매니저 CareLog note 학부모 공개분"으로 설계됨). 매니저가 케어로그를 남기는 것 자체가 리포트 콘텐츠 생산 → 별도 리포트 작성 부담 0.
- **근거·출처**: `schema.prisma:567` managerComment 주석, `ManagerCareLog:351` visibleToStudent. 기 구현 자산 연결(R2b: ManagerCareLog 실존).
- **구현 가능**: 웹
- **임팩트**: 리포트 인간미(§11-7 "인간의 결"), 매니저 노동의 자산화
- **시기**: **A** (P-6 동승)
- **리스크**: 내부 메모 오노출 → visibleToStudent 기본 false 확인.

### P-10. 성적 추이 = 시험 결과 이벤트 수기 입력 (내신·모의고사 노드)
- **상세**: overallScore(완수율 기반)와 별개로, 실제 시험 성적(내신/모평 등급) 변화를 매니저/강사가 이벤트로 기록. `ConsultationReport.goals`의 정량목표("4→2등급") 대비 실적을 마일스톤으로. 신규 스키마 최소(성적 이벤트 1테이블 or CareLog type 확장). 이것이 케이스스터디(P-7)의 **가장 강한 팩트**.
- **근거·출처**: 리서치(성적 향상=학부모 만족 결정요인, tutoring effectiveness 연구). C-9 케이스스터디의 하드 팩트. 정성목표 아닌 정량 실적.

- **임팩트**: 위기 감지 누락↓

**관통 논지**: 이 웨이브의 핵심은 "신규 개발"이 아니라 **이미 코드에 설계된 데이터 자산의 각성**이다. ConsultationReport·MonthlyReport·OnboardingSurvey·SatisfactionCheckin·HomeworkTemplate·ManagerCareLog는 스키마와 읽기 경로가 실존하고 쓰기·활용만 비어 있다. 프리미엄 큐레이션이 팔아야 할 "증거"(진단·리포트·안심)가 스키마 레벨에 이미 있으므로, R2-skeptic이 "오버엔지니어링·조기 스키마"로 연기한 다수 안이 **기존 자산 활용으로 파일럿 즉시 실행 가능**해진다. 데이터 자산화 = 증거 자동 생산 라인 = 리텐션·전환·강사유지의 공통 뿌리.
