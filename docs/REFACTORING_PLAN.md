# 리팩토링 제안 (Refactoring Plan)

> 작성: 2026-07-04 · **갱신: 2026-07-05** — 1개월 히스토리 진단(커밋 155건·feat 78:fix 32:refactor 1) 기반 R-12~16 추가 + R-1/2/4 상태 정정.
> 원칙: 파일럿 개시 전에는 **보안·데이터 정합성(P0~P1)만** 처리하고, 구조 개선(P2)은 기능 개발과 충돌하지 않는 시점에 점진 수행. 리팩토링을 위한 리팩토링은 하지 않는다. **스프린트당 리팩토링 지분 ≤20%** — 리팩토링은 독립 프로젝트가 아니라 다음 피처의 통행세로 낸다.

## P0 — 보안 (파일럿 개시 전 필수)

### R-1 · Toss 웹훅 서명 검증 부재 — ✅ 해소 (2026-07-05 정정)
- **정정**: Toss는 HMAC 서명을 제공하지 않음. 웹훅 수신 시 `fetchTossPayment`로 Toss API를 재조회해 검증하는 현행 패턴이 올바른 구현이며 이미 적용되어 있음 (S1-2 실측). 추가 작업 불필요 — 종결.

### R-2 · Supabase RLS 미설정
- **현황**: DB 접근이 Prisma(서비스 롤) 단일 경로라 당장 노출은 없으나, anon 키가 클라이언트에 존재하는 이상 RLS 부재는 방어선 0개.
- **제안**: 최소한 전 테이블 `DENY ALL` 기본 정책 적용(Prisma는 서비스 롤이므로 영향 없음). 테이블별 정밀 정책은 모바일 앱이 Supabase 직접 접근을 쓰게 될 때 재설계.
- **상태 (2026-07-05)**: ✅ SQL 준비 완료 — `prisma/manual/20260705_rls_and_storage_policies.sql` (S1-5, 커밋 98d5715). **적용은 경영자 승인(E4-5) 후 수동 실행 대기.**

### R-3 · CHIEF_MANAGER 미들웨어 경로 검증 [확인 필요]
- **현황**: TECH_OVERVIEW §8에 "미확인"으로 기재. API 레이어는 `requireChiefManagerOrAdmin`(`src/lib/admin-auth.ts`)으로 보호되나, **페이지 미들웨어**가 CHIEF_MANAGER 전용 경로를 올바르게 게이트하는지 미검증.
- **제안**: 확인 태스크 — `middleware.ts`의 role 분기 표를 만들어 4역할×주요 경로 매트릭스로 검증. 구멍 발견 시에만 수정.
- **규모**: 소 (확인 2시간).

## P1 — 데이터 정합성·안정성

### R-4 · QnA 모델 이중화 해소 (`Question` → `QuestionMessage`)
- **현황**: 구 `Question` 모델과 신 `QuestionMessage` 모델이 공존 (TECH_OVERVIEW §8). 읽기·쓰기 경로가 갈라져 있어 신규 기능마다 분기 비용 발생.
- **제안**: ① 구 데이터 → 신 모델 백필 마이그레이션 ② 읽기 경로 통일 ③ 구 모델 쓰기 차단 ④ 한 릴리스 뒤 모델 제거. 데이터가 적은 지금(파일럿 전)이 마이그레이션 최적기.
- **상태 (2026-07-05)**: 🔶 부분 해소 — 7/4 「feat(qna): unify web and mobile QnA on QuestionMessage」로 읽기·쓰기 경로 통일 완료. 잔여: 구 `Question` 모델 제거(④단계)만 남음.
- **규모**: 중 (1~2일).

### R-5 · Journey 상태 드리프트 (`FIRST_LESSON_PENDING`)
- **현황**: 학생 여정 상태가 실제 진행과 어긋나는 드리프트 존재 (TECH_OVERVIEW §8). 매니저 화면의 신뢰도 문제 — 운영이 시작되면 매니저가 잘못된 상태를 보고 행동하게 됨.
- **제안**: 상태 전이를 단일 함수로 수렴(전이 규칙 표 기반), 드리프트 검출 배치를 `run-alert-checks`에 추가.
- **규모**: 중.

### R-6 · `connection_limit=1` 병렬 쿼리 제약
- **현황**: Prisma 연결 1개 제약으로 `Promise.all` 병렬 쿼리 금지가 **암묵 규약**으로만 존재. 위반해도 로컬에서는 통과하고 프로덕션에서만 간헐 실패하는 최악의 부채 유형.
- **제안**: ① `src/app/api` 전수 grep으로 현존 위반 감사 ② ESLint 커스텀 룰 또는 최소한 CLAUDE.md/AGENTS.md에 규약 명문화 ③ 중기적으로 Supabase pooler(pgbouncer) 경유로 limit 상향 검토.
- **규모**: 감사 소 / 근본 해소 중.

### R-7 · 정산 시급 상수의 데이터 이관
- **현황**: `src/lib/settlement.ts`의 `TEACHER_HOURLY_RATE_KRW` 하드코딩. 현재는 단순함이 미덕이지만, `BM_EVOLUTION.md` BM-A(등급별 차등 시급)가 채택되면 즉시 병목.
- **제안**: 지금은 유지. BM-A 착수 결정 시 Teacher 레코드 필드(+변경 이력 테이블)로 이관. **선제 구현 금지** — BM 결정에 종속.
- **규모**: 중 (BM-A 채택 시).

## P1.5 — 1개월 히스토리 진단 기반 추가 (R-12~16, 2026-07-05)

> 근거: 6/16~7/5 커밋 155건 진단 — feat 78 : fix 32 : refactor 1, 테스트 0개, API 라우트 111개. 결론: 오버엔지니어링이 아니라 **의도적 언더엔지니어링으로 속도를 사는 중이며 대체로 옳음.** 단, 무인 과금(빌링키 자동갱신)이 들어온 시점부터 "테스트 0"은 속도가 아니라 리스크. 아래 5건은 그 임계점만 도려내는 최소 세트다.

### R-12 · 돈 경로 통합 테스트 (신규 — 유일한 "선행" 항목) 🔴
- **현황**: 결제 confirm·환불·빌링키 자동갱신·정산이 전부 수동 검증(pilot-verify)에만 의존. 회귀는 시간이 아니라 변경 횟수의 함수 — 111개 라우트·월 110건 feat/fix 속도에서 임계점 도달.
- **제안**: vitest 도입 + **결제 상태 전이 불변식만** 10~15개 통합 테스트: confirm 멱등성 / 환불 순서(Toss 취소 성공 → DB 전환) / `ALREADY_CANCELED_PAYMENT` 처리 / 웹훅 CANCELED 수렴 / 레이스(updateMany count=0 → 409) / 더닝 재시도. Prisma는 테스트 DB 또는 모킹 중 **실 DB 스키마 검증이 가능한 쪽** 선택.
- **경계**: 커버리지 %목표 금지. UI·CRUD 테스트 금지. "돈과 권한 불변식"을 벗어나는 테스트는 리뷰에서 거부.
- **시점**: **S2 착수 전 반세션.** 규모: 소~중.

### R-13 · `run-alert-checks` 체크 레지스트리 전환 (R-8 항목의 승격)
- **현황**: 1,834줄, 최근 1개월 순증 +1,679줄 — 코드베이스에서 가장 빠르게 자라는 파일. 모든 알림·체크가 단일 cron 런에 순차 결합: 체크 1개의 예외가 전체 런을 죽일 수 있고, Vercel 함수 시간 한도에 수렴 중. S2(72h 시퀀스·주간 요약·리캡)가 전부 이 파일에 얹힐 예정이라 방치 시 2,500줄+.
- **제안**: 체크 1개=모듈 1개 레지스트리 — 각 체크는 `{ name, run() }` + 자체 try/catch + 소요 시간 로그 + 멱등 키. **S2-1을 새 구조에 먼저 넣고** 기존 체크는 터치할 때만 이주(빅뱅 이주 금지).
- **시점**: S2-1 구현과 동시(독립 리팩토링 금지). 규모: 골격 소, 이주 점진.

### R-14 · 랜딩 구버전 삭제
- **현황**: `LandingPage`(1,890줄 churn)·`LandingPageThemed`(1,360)·`LandingPageV2`(2,432) 3벌 공존. 죽은 버전은 검색 노이즈 + "어느 게 진짜냐" 판단 비용.

### R-15 · 인증 관용구 표준화 (R-3·R-10의 실행판)

### R-16 · CMS 오버레이 동결 (코드 0, 정책 결정)
