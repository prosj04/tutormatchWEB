## Part 1-A — 사업 측면 리스크

### BR-1. 재결제 구조가 없다 — 이 사업의 기본값은 "이탈"이다

**사실 확인**: `Subscription.periodEnd`는 결제 시점 +1개월로 박히고(`student-payment.ts:72`), 토스 연동은 일회성 위젯뿐이다(빌링키/자동결제 없음). **만료 임박 알림도, 재결제 버튼도, 만료 후 처리도 코드에 없다.** 학부모가 매달 스스로 `/checkout`을 다시 찾아와야 하는데 그 동선조차 없다.

구독 사업이 아니라 **매달 신규 판매를 반복하는 구조**다. 과외 시장에서 첫 달 만족한 고객의 재결제는 가장 쉬운 매출인데, 지금은 그 매출이 시스템적으로 새고 있다.

**실행**:
1. (즉시, 코드 소) Cron에 `checkSubscriptionExpiry()` — `periodEnd` D-5·D-1에 학생 알림+푸시, 앱/웹에 "이용권 연장" 버튼 → 기존 checkout 재사용 (plan 프리필).
2. (다음 분기) 토스 **빌링키 자동결제** 전환 — 정기결제 동의 UI 포함. 이때 환불·해지 규정(BR-4)이 선행돼야 한다.
3. 만료 후 상태 정의: `PAST_DUE` 시 AI 토큰 차단은 이미 quota로 동작하나, 수업·플래너 접근 정책을 명시적으로 정할 것 (권장: 열람 허용·작성 제한 — 데이터 인질극은 신뢰 훼손).

### BR-2. 탈중개(직거래 전환) 방어선이 없다 — 그리고 강사 정산 시스템이 코드에 전무하다

**사실 확인**: 대면 수업 모델이라 첫 수업부터 학부모와 강사가 직접 만난다. 플랫폼 이용료(과목당 월 3.5~6만)를 아끼려는 직거래 유인은 이 업종의 고전적 붕괴 경로다. 방어 수단은 "플랫폼에 남아야 할 이유"(리포트·플래너·질답·매니저 관리)인데, `docs/PRODUCT_DESIGN_TRACKER.md`에서 확인했듯 **리포트·학습그래프가 죽어 있어 락인이 사실상 매니저 한 명의 인간관계뿐**이다.

더 근본적으로: **강사 정산(Payout) 모델·코드가 아예 없다.** 수업료가 강사에게 어떻게 가는지가 시스템 밖(수기)에 있다는 뜻이고, 이는 ① 규모 확장 불가 ② 수업 실적 기반 정산 근거 부재(BR-4와 결합) ③ 직거래 감지 불가(정산 데이터가 없으니 수업이 줄었는지도 모름)를 의미한다.

**실행**:
1. 락인 = FI-1(월간 리포트)·FI-3(학습 그래프) 활성화가 곧 탈중개 방어다 — 우선순위 근거로 추가.
2. 강사와의 계약서에 직거래 금지·위약 조항이 있는지 점검 (시스템 이전에 계약 문제).
3. `Payout` 설계 전이라도 최소한 **수업 실적 원장**은 확보할 것 — EC-7의 `Lesson COMPLETED` 전환이 그 기초 데이터다 (수업이 안 찍히면 정산도 분쟁 방어도 불가능).

### BR-3. Chief 매니저 단일 깔때기 — 처리량과 지역이 한 사람에게 묶여 있다

**사실 확인**: 결제 학생 전원이 Chief 1명에게 자동 배정되고(`assignChiefManagerToStudent`), 대면 상담이 필수 단계다. 즉 **월 신규 결제 상한 = Chief 한 명의 방문 상담 캘린더**이고, 서비스 가능 지역 = 그 사람의 이동 반경이다. 휴가·퇴사 시 신규 유입이 멈춘다(bus factor 1).

**실행**:
1. 단기: `CHIEF_MANAGER_EMAIL` 부재·오류 시 경고(EC-9) + 매니저별 배정 부하는 Admin 통계에 이미 있으니 **주간 상담 처리량 임계 알림** 추가.
2. 성장 시: 배정 라우팅을 학생 지역 기반으로 — 가입/설문(FI-4)에 지역 필드를 넣어 두면 나중에 스키마 변경 없이 라우팅 로직만 추가하면 된다. **지금 지역 데이터를 안 모으는 것이 미래 확장의 실질 병목**이다.

### BR-4. 선불 고액 + 환불 규정·수업 기록 부재 = 분쟁에서 무조건 진다

**사실 확인**: 월 38~112만원 선불인데 ① 환불·중도해지 규정이 요금제/체크아웃 어디에도 없고(푸터 링크만, 라이브 확인) ② `Lesson.status`가 영원히 `SCHEDULED`라(EC-7) **몇 회 수업이 실제 진행됐는지 시스템 기록이 0**이다. "8회 중 5회만 했으니 환불해달라"는 분쟁에서 플랫폼이 제시할 데이터가 없다. ③ 라이브 푸터에 **통신판매업신고번호가 없다** — 온라인 결제를 받는 순간 전자상거래법상 신고·표시 의무 대상이다.

**실행**:
1. (법무, 코드 아님) 통신판매업 신고 + 환불 규정 문서화 — 회차 기준 일할 환불이 업계 표준. 학원법 적용 여부(교습소·개인과외교습자 신고)는 사업 형태에 따라 전문가 확인 필요.
2. (코드 소) 환불 규정 요약 3줄을 `checkout_page` CMS 섹션에 추가해 결제 버튼 위 노출.
3. EC-7 수업 완료 처리 + 강사의 수업 완료 확인 UI(출석 기록)를 P1로 승격 — 정산(BR-2)·환불(BR-4)·리포트(FI-1) 세 가지의 공통 기초 데이터다.

### BR-5. 하이터치 운영 vs 얇은 테이크레이트 — 단위경제 측정 데이터가 없다

**사실 확인**: 표시 요금 기준 플랫폼 이용료는 과목당 월 3.5만(4회)/6만(8회) — 월 38만 상품에서 약 9%. 그런데 원가에는 매니저 방문 상담, 학습 모니터링, 리포트, 재매칭 보장이 들어간다. 매칭만 하는 저테이크 모델과 밀착 관리형 고테이크 모델의 **원가 구조를 갖고 가격은 중개 수수료 수준**이다. (수업료 몫의 마진 구조는 코드·문서에 없어 판단 불가 — 정산 시스템 부재와 같은 뿌리.)

**실행**: 가격 인상보다 먼저 측정 — 학생 1명당 매니저 터치(상담·모니터링 알림 처리) 횟수는 기존 `Notification`·`ConsultationBooking` 데이터로 추출 가능하다. Admin 통계에 "매니저 시간당 관리 학생 수"를 추가하고, 그 수치가 나온 뒤 이용료 vs 관리 강도를 조정할 것. 측정 없이는 이 리스크는 판단 불가로 남는다.

### BR-6. 미성년자 대면 수업인데 신원 검증이 "서류·면접"뿐

**사실 확인**: 라이브 사이트의 안전 관련 문구는 "서류·면접 검증, 명문대 검증 강사"가 전부다. 학력 증빙 업로드는 구현돼 있으나 **범죄경력·성범죄경력 조회 절차가 제품·문구 어디에도 없다.** 학원·교습소는 아청법상 성범죄경력 조회가 의무이고, 중개 플랫폼 형태라도 사고 1건이 사업 전체를 끝낼 수 있는 영역이다. 역으로, 선제 도입하면 학부모 대상 최상급 차별화 포인트가 된다.

**실행**: (운영) 강사 온보딩에 성범죄경력회신서 제출 단계 추가 → (코드 소) `TeacherProfile.documentUrls`에 서류 타입 구분 추가 + 승인 화면 체크리스트 → (마케팅) 검증 절차를 사이트에 명시 (MK-8과 연결).

**결론 — "없으면 없다"에 대한 답**: 없는 게 아니라, 이 유형 플랫폼의 3대 고전 리스크(탈중개·재결제·분쟁)가 모두 실재하며, 셋 다 공통 원인이 "수업 실적이 시스템에 안 찍힌다"로 수렴한다. EC-7이 코드 이슈처럼 보이지만 실은 사업 인프라다.

## Part 1-B — 홈페이지 / 마케팅 (라이브 실사 기반)

### MK-1. 🔴 푸터에 더미 데이터가 실서비스로 노출 중 — 오늘 고칠 것 ✅(부분 해소됨: SNS 링크 미노출 처리 완료 — DESIGN §7. 사업자 정보는 미해소)

**확인된 사실**: 라이브 푸터가 **대표자 "홍길동", 사업자등록번호 "123-45-67890"**, 주소 "테헤란로 000, 00층". 고액 선불 결제 전에 학부모·학원 커뮤니티가 가장 먼저 하는 일이 사업자 조회다. 조회 불가능한 더미 번호는 이탈이 아니라 **사기 의심**을 만든다. 통신판매업신고번호 표기도 없다(BR-4).

**실행**: `footer` CMS 섹션(`/admin/cms`)에서 실제 상호·대표자·사업자번호·주소·통신판매업신고번호로 교체 — **코드 변경 불필요, 오늘 가능**. 실 정보 확정 전이라면 차라리 항목을 비노출하는 게 더미보다 낫다.

### MK-2. 🔴 강사진 페이지: 기본 아바타 7명 + 샘플 계정 — "명문대 검증 강사" 주장과 정면 충돌 ✅(해소됨: 공개 목록 필터로 처리 — 커밋 0eefa8c)

**확인된 사실**: `/tutors`에 약 7명, 전원 `default-male.png`/`default-female.png` 기본 아바타, 일부는 샘플 계정, 평점·후기 0. 홈에서 "1,200+ 매칭 완료"를 주장하는데 강사가 7명(그마저 샘플 포함)이면 학부모의 교차검증에서 신뢰가 무너진다. 강사진 페이지는 이 서비스에서 상담 신청 직전 마지막 확인 페이지다.

**실행**:
1. (오늘) 샘플 계정 `approved: false` 처리로 비노출.
2. 실제 강사 실사진 확보가 안 되면 페이지 콘셉트를 "전체 목록"에서 **"대표 강사 큐레이션"**으로 전환 — 3~4명이라도 실사진+상세 스토리(교육 철학, 성적 향상 사례 1건씩)가 아바타 7명보다 강하다.
3. 사진 없는 강사는 목록에서 제외하는 노출 규칙 추가 (`public-teachers-cache.ts` 필터 1줄).

### MK-3. 대면 서비스인데 서비스 지역이 어디에도 없다

**확인된 사실**: 홈·요금제 모두 지역 안내 없음 (라이브 확인). 방문 상담 + 대면 수업 모델에서 이건 양방향 손실이다 — 지역 밖 학부모는 상담 신청 후에야 안 된다는 걸 알게 되고(매니저 시간 낭비 + 나쁜 경험), 지역 안 학부모는 "우리 동네도 되나?" 불확실 상태로 이탈한다.

**실행**: ① 히어로 서브카피 또는 뱃지에 서비스 지역 명시("서울·분당 방문 수업" 식) — `hero` CMS로 가능. ② FAQ 1번 항목으로 승격. ③ 상담 신청 폼에 지역(구 단위) 필드 추가 → BR-3의 라우팅 데이터로도 축적.

### MK-4. 38~112만원 선불 결제 직전에 환불 이야기가 없다

**확인된 사실**: 요금제 페이지에 환불·중도해지 언급 0 (푸터 링크뿐). 유일한 불안 해소 장치는 "첫 배정 강사가 맞지 않으면 추가 비용 없이 재매칭" — 이건 좋은 카피인데 고립돼 있다. 고액 선불의 마지막 이탈 사유는 "돈이 묶이면 어떡하지"다.

**실행**: 요금제 카드 하단 + 체크아웃 결제 버튼 위에 2줄 고정 노출 — "중도 해지 시 미진행 회차 환불 / 첫 강사 무료 재매칭" (`pricing_page`·`checkout_page` CMS). 규정 자체는 BR-4 법무 선행.

### MK-5. 고가 상품에 진입 사다리가 없다 — 그런데 이미 갖고 있는 걸 안 쓰고 있다

**확인된 사실**: 체험·첫 달 할인·무료 진단 등 진입 장치 전무 (라이브 확인). 그런데 이 서비스의 무료 방문 상담이 **사실상 무료 진단 상품**인데, 요금제 페이지에서는 "이 플랜으로 시작"(바로 결제)과 병렬로만 존재한다. 학부모 구매 심리는 "진단받고 → 납득하고 → 결제"인데 페이지 구조는 결제 우선이다.

**실행**: ① 요금제 페이지 상단에 "먼저 무료 방문 상담으로 맞춤 플랜을 추천받으세요" 경로를 시각적 1순위로, 결제는 "이미 플랜을 아는 분" 보조 경로로 재배치. ② 단, 결제 우선이 옳을 수도 있으므로 **FI-6 퍼널 이벤트를 먼저 심고 2주 데이터로 판단** — 지금은 어느 쪽이 이기는지 측정조차 불가하다.

### MK-6. 수치 주장이 교차검증을 못 버틴다

**확인된 사실**: "500+ 누적 상담, 1,200+ 매칭 완료, 98% 만족도" vs 강사 7명·평점 0건·익명 후기. 큰 수치는 페이지 안의 다른 증거와 모순되는 순간 모든 주장의 신뢰를 같이 끌어내린다.

**실행**: 검증 불가능한 총량 수치를 빼고, 검증 가능한 구체 증거로 교체 — 이미 갖고 있는 "수학 5등급→2등급, 영어 64→87점" 류의 사례를 늘리는 방향(과목·기간·지역 포함 스토리형). `stats` CMS 섹션 수정으로 가능. FI-2(실후기 파이프라인)가 장기 해법.

### MK-7. 한국 학부모 타깃인데 카카오톡 채널이 없다

**확인된 사실**: 연락 수단이 "채팅 10:00~22:00, 전화(평일)" 표기뿐 — 전화번호 자체는 비노출이고 카카오톡 채널 부재. 이 타깃(40대 학부모)의 기본 문의 채널은 카톡이다. 상담 신청 폼(가입 필요)이 유일한 실질 접점이면, 가입이 부담스러운 초기 관심층을 전부 버리는 구조다.

**실행**: 카카오톡 채널 개설(무료) → 전 페이지 플로팅 버튼 추가 (기존 `FloatingConsultationCue` 컴포넌트 옆 또는 통합, 반나절 작업). 채널 응대는 매니저 업무에 편입.

### MK-8. 진짜 차별화(전담 매니저 밀착 관리)가 히어로에 없다

**확인된 사실**: 히어로는 "아이마다 맞는 선생님이 다릅니다" + 무료 상담 CTA — 모든 과외 매칭 앱이 하는 말이다. 이 서비스의 실제 차별화는 **매니저가 방문 상담으로 직접 매칭하고, 매칭 후에도 플래너·질답·리포트로 관리한다**는 것(비교 테이블에는 있음)인데, 첫 화면 3초 안에 전달되지 않는다. BR-6의 신원검증까지 갖추면 "매니저 검증·관리형"은 김과외·숨고류 셀프 매칭과의 명확한 포지셔닝이다.

**실행**: 히어로 서브카피를 차별화 서술로 교체 — 예: "전담 매니저가 직접 방문 상담하고, 수업 시작 후에도 매주 학습을 관리합니다" (`hero` CMS). 신뢰 뱃지 라인(신원검증·재매칭 보장·환불 보장)을 히어로 바로 아래 배치.

## A. 법률 — 개시 블로커 (결제를 받는 순간 문제가 되는 것)

### BR-7. 🔴 약관·개인정보처리방침·환불정책이 전부 "준비 중" 플레이스홀더

**리스크**: ① 약관 없이 결제 = 분쟁 시 회사가 주장할 계약 조건이 없음. ② **개인정보처리방침은 개인정보보호법상 수립·공개 의무** — 지금도 가입으로 이름·전화번호를 수집 중이므로 개시 전이 아니라 **현재 시점 위반 상태**다. ③ 환불정책 부재는 BR-4(전자상거래법 청약철회 고지)와 직결.

**실행**:
1. (법무) 3종 문서 작성 — 과외 중개 표준약관 기반 + 환불은 회차 일할 기준.
2. (Claude Code) 3개 페이지를 CMS 연동으로 전환: `SiteContent` section `legal_terms`/`legal_privacy`/`legal_refund` (type text, 마크다운 렌더) → 법무 수정을 배포 없이 반영. 가입 폼(`ConsultationSignupForm`)과 체크아웃에 **약관·개인정보 동의 체크박스 + 동의 시각 저장** (`User`에 `termsAgreedAt DateTime?`, `privacyAgreedAt DateTime?` — §2 마이그레이션에 동승).

### BR-8. 🔴 초등학생(만 14세 미만)이 가입 대상인데 법정대리인 동의 절차가 없다

**사실 확인**: 학년 선택지에 **초등 1~6학년 포함** (`consultation-grades.ts:3-8` 실측). 가입 수집 필드는 `name, grade, subjects, phone, password, gender`가 전부 — 생년월일도, 보호자 정보도, 14세 미만 분기도 없다 (`api/register/student/route.ts:38` 실측).

**리스크**: 개인정보보호법 제22조의2 — **만 14세 미만 아동의 개인정보 수집에는 법정대리인 동의가 필수**. 초등생 타깃을 명시한 서비스에서 이 절차 부재는 명백한 위반이고, 과징금 대상이다.

**실행** (Claude Code):
1. `Student`에 `guardianName String?`, `guardianPhone String?` 추가 (§2 마이그레이션 동승).
2. 가입 폼에서 학년이 초등~중1이면 보호자 이름·전화 필수 + "법정대리인 동의" 체크 → `guardianConsentAt DateTime?` 저장. 동의 확인 SMS(기존 Solapi 인프라)를 보호자 번호로 발송하면 동의 증빙이 된다.
3. 사실상 학부모가 가입을 대행하는 현재 행태를 양성화: 가입 1단계에 "학부모입니다 / 학생 본인입니다" 선택을 추가하고 학부모 선택 시 보호자 필드를 기본 수집. → BR-9의 해결 기반이기도 하다.

### BR-9. 🔴 미성년자 명의 결제 — 민법상 언제든 취소당할 수 있는 매출

**사실 확인**: 결제(`/checkout`)는 `STUDENT` 계정 세션으로 진행되고 결제자(보호자) 정보를 받는 필드가 없다.

**리스크**: 미성년자가 법정대리인 동의 없이 한 계약은 **민법상 취소 가능** — 취소되면 전액 반환. 월 38~112만원 결제가 학생 명의로 잡히는 구조는 "몇 달 뒤 일괄 취소+환불" 시나리오에 무방비다. 토스 심사에서도 미성년자 거래 정책을 본다.

**실행**: 체크아웃에 결제자(보호자) 성명·관계 확인 단계 + "본인은 학생의 법정대리인으로서 결제에 동의합니다" 체크 → `PaymentCompletion`에 `payerName`·`payerConsentAt` 기록. BR-8의 보호자 정보를 프리필.

### BR-11. 광고 수치의 근거 보존 의무

**사실 확인**: 홈에 "98% 학생 만족도, 1,200+ 매칭" 등 수치 게시 (개시 전 교체 예정이라 해도 구조는 동일).

## B. 개인정보 · 보안 · 데이터

### BR-12. 🔴 결제·거래 기록이 학생 삭제와 함께 연쇄 삭제된다 — 법정 보존 의무 위반 구조

**사실 확인**: `PaymentCompletion`·`Subscription` 모두 `student … onDelete: Cascade` (`schema.prisma:311,327` 실측). Admin 학생 CRUD에 삭제가 있으므로, **학생 1명을 지우면 그 학생의 모든 결제 기록이 DB에서 소멸**한다.

**리스크**: 전자상거래법상 계약·대금결제 기록 **5년 보존 의무**. 회원 탈퇴(BR-13)를 구현하는 순간 이 문제가 매번 발생한다. 세무 조사·환불 분쟁 시 근거 소멸.

**실행** (Claude Code, §2 마이그레이션 동승):
1. `PaymentCompletion`·`Subscription`의 relation을 `onDelete: Restrict`로 변경하고 `studentId`를 유지한 채 스냅샷 필드(`studentNameSnapshot`) 추가, 또는 학생 삭제를 soft delete로 전환 (`Student.deletedAt` + 조회 필터).
2. 권장: **soft delete 방식** — 삭제 요청 시 개인정보 필드(name→"탈퇴회원", phone→null 등)를 파기하되 거래 레코드는 보존. 개보법(파기)과 전상법(보존)을 동시에 충족하는 표준 패턴이다.

### BR-13. 🔴 회원 탈퇴 기능이 없다 — 개보법 + 앱스토어 심사 이중 블로커

**사실 확인**: API 58개 목록·모바일 라우트 어디에도 계정 삭제 엔드포인트가 없다.

**리스크**: ① 개인정보보호법상 파기 요구권 — 탈퇴 수단 미제공은 위반. ② **Apple App Store 심사 가이드라인 5.1.1(v): 계정 생성이 있는 앱은 계정 삭제 기능 필수** — Expo 앱 제출 시 100% 리젝 사유다. Google Play도 동일 정책.

**실행** (Claude Code): `DELETE /api/mobile/me` + 웹 `POST /api/account/delete` 신규 — BR-12의 soft delete 파기 로직 호출, 활성 구독 있으면 환불 안내 후 진행, 앱 MY 탭·웹 설정에 탈퇴 UI. 재확인 다이얼로그 + 30일 유예(선택).

### BR-14. Supabase RLS·스토리지 정책 미설정 — 강사 신분증·이력서가 들어가는 곳

**사실 확인**: 버킷 자체는 `teacher-documents`·`question-images` private, `teacher-photos` public으로 생성된다 (`scripts/setup-storage.ts:17-19` 실측 — 설계는 올바름). 그러나 핸드오프 §13이 명시하듯 **RLS 정책이 코드에 없고 대시보드 수동 설정에 의존**한다. 정책이 비어 있으면 anon key 업로드 경로가 과다 권한이거나, 반대로 프로덕션에서 조용히 실패한다.

**리스크**: `teacher-documents`에는 이력서·증빙(주민번호 포함 가능성), `question-images`에는 미성년자의 필적·노트 사진이 들어간다. 유출 시 개보법 사고 신고 대상.

**실행**: ① (운영) 프로덕션 Supabase에서 3개 버킷의 정책 실사 — 특히 anon 역할의 read/list 권한. ② (Claude Code) `scripts/setup-storage.ts`에 권장 정책 SQL을 주석이 아닌 실행 코드로 추가(멱등), 업로드 경로를 서버 라우트 경유(service role)로 통일하는 리팩터를 P2로. ③ 저장소 루트의 `admin_cookies.txt`·`cookies.txt`는 세션 쿠키 파일 — 삭제하고 `.gitignore`에 추가 (커밋되기 전에).

### BR-15. 개인정보 취급 감사 로그 부재

**사실 확인**: Admin·매니저가 학생 개인정보를 열람·수정·삭제한 기록이 없다 (Notification·AnalyticsEvent 어디에도 관리자 행위 추적 없음).

**리스크**: 개인정보 안전성 확보조치 고시 — 개인정보취급자의 **접속기록 1년 이상 보관** 의무. 내부자 유출 사고 시 추적 불가.

**실행** (Claude Code): `AuditLog` 모델 신규 (`actorUserId, action, targetType, targetId, meta JSON, createdAt`) + `requireAdmin`/`requireManager`를 통과하는 변경성(POST/PATCH/DELETE) 라우트에 기록 헬퍼 1줄 삽입. Admin 조회 화면은 P3.

### BR-16. 매칭 후 연락처 노출 범위 미정의

**확인 필요 사항**: 매칭 후 학생 전화번호가 강사에게(또는 역방향) API로 노출되는지 — `GET /api/teacher/students` 응답 필드를 점검할 것. 노출된다면 ① 개인정보 최소제공 원칙, ② BR-2(직거래)의 기술적 방조가 된다.

**실행**: 정책 결정이 먼저 — 권장: 첫 수업 확정 전까지는 연락처 비노출, 연락은 매니저 경유. 이후 (Claude Code) 해당 API select에서 phone 제거 또는 단계 조건부 노출.

## C. 재무 · 세무

### BR-17. 강사 지급 원천징수 — 정산 시스템 부재(BR-2)의 세무 버전

수기 정산이라도 사업소득 3.3% 원천징수 + 반기 지급명세서 제출 의무는 발생한다. 개시 첫 달부터 지급 대장(강사·월·수업 수·지급액·원천세) 스프레드시트라도 운영할 것. 시스템화는 BR-2의 `Payout` 설계와 통합.

### BR-18. 부가세 혼합 거래 — 결제 구조가 이미 분리돼 있는 점을 활용

**사실 확인**: 체크아웃이 수업료 vs 플랫폼 이용료를 분리 표시한다 (`order-pricing.ts`). 과외 용역(면세 가능성)과 중개 수수료(과세)는 세무 처리가 다르다 — 지금 총액 단일 결제라 세금계산서·현금영수증 발급 구분이 없다.

**실행**: (세무사 확인 후) `PaymentCompletion`에 `tuitionAmount`/`feeAmount` 분리 저장 (§2 마이그레이션 동승, 이미 계산 로직 존재) + 현금영수증 발급은 토스 API가 지원하므로 E1 서버 승인 구현 시 함께.

### BR-19. 선수금 = 부채 — 환불 재원 분리

월 선불 매출은 수업 진행 전까지 회계상 부채다. 초기에 선수금을 운영비로 소진하면 환불 대량 발생 시(BR-9 미성년자 취소 등) 지급 불능. 운영 수칙: 월말 미진행 회차 상당액은 별도 계좌 유지. (코드: EC-7 수업 기록이 미진행 회차 계산의 기초 데이터.)

## D. 운영 정책 공백 (분쟁 1순위 후보들)

### BR-20. 수업 취소·보강·이월 규정이 시스템에도 약관에도 없다

**사실 확인**: `Lesson.status`에 `CANCELLED`는 있지만 보강·회차 이월 개념이 없고, 월 회차제(월 4회/8회)인데 "이번 달 3회밖에 못 했으면?"의 답이 어디에도 없다. 과외 서비스 CS의 최다 빈도 이슈다.

**실행**: ① (정책) 취소 통보 시한(24h 전), 보강 원칙, 이월 상한을 환불정책과 함께 문서화. ② (Claude Code, P2) `Lesson`에 `rescheduledToId String?` 추가 + 취소 시 보강 수업 생성 플로우, 월별 진행 회차 카운터를 학생·매니저 화면에 표시 (EC-7 COMPLETED 전환이 선행 조건).

### BR-21. 강사 중도 이탈 시 학생 인계 절차 부재

강사가 그만두면: 위탁계약서에 사전 통보 기한·인수인계 의무 명시(법무) + 시스템은 EC-1의 재매칭 플로우 재사용 — `TeacherStudent`를 `ENDED` 처리하고 매니저에게 재매칭 태스크 알림. 잔여 회차는 신규 강사로 승계됨을 환불정책에 명시.

### BR-22. 배상책임보험 미확인

가정 방문 대면 수업 = 수업 중 사고·기물 파손·이동 중 사고의 접점. 과외·교육 서비스용 영업배상책임보험은 저렴하다 — 개시 전 가입하고 "보험 가입 완료"를 신뢰 요소(MK-8 뱃지)로 역이용할 것.

### BR-23. 매니저·강사의 노무 분류

매니저는 배정을 받고 지휘·감독 하에 상시 업무를 수행하는 구조(시스템이 그렇게 설계됨) — 프리랜서 계약이라면 **근로자성 인정 리스크**(퇴직금·4대보험 소급)가 크다. 매니저는 근로계약 권장. 강사는 위탁계약 + 업무 지시 최소화 원칙 (플랫폼이 수업 방식을 지시할수록 근로자성이 올라간다 — 숙제 분배 같은 도구 제공은 무방, 강제는 주의).

## 2. 🔴 계측 제로 상태 — 마케팅 집행 전에 "무엇이 전환인지"부터

- 코드 확인 결과 GA4·픽셀·Vercel Analytics 등 **어떤 분석 도구도 없음**. 지금 광고를 집행하면 돈이 어디서 새는지 알 수 없음.

  2. 전환 이벤트 4개만 정의: `상담_신청_제출`(핵심), `플로팅CTA_클릭`, `요금제_카드_클릭`, `전화_클릭`
  3. 광고 시작 시점에 카카오 픽셀·네이버 프리미엄로그 추가

## 3. 🟠 사진 전략 — AI 생성은 브릿지, 본안은 반나절 실촬영

- AI 실사(현재 보류 중, `PHOTO_GENERATION_PROMPT.md`)는 빠르지만: ① 후기·블로그·광고 소재로 재사용 불가(인물 일관성), ② "실제와 다를 수 있음" 면책 필요, ③ 학부모 커뮤니티에서 AI 사진 판별 시 역풍 리스크.
- **제안**: 초기 합류 선생님 2~3명 + 매니저로 반나절 스튜디오 촬영 (지역 스튜디오 기준 수십만 원대). 한 번의 촬영으로 → 홈 카드 + 강사 상세 + 블로그 + 카카오 채널 프로필 + 광고 소재까지 전부 해결. AI 사진은 촬영 전까지의 임시 브릿지로만.

## 4. 🟠 네이버 생태계 — 한국 학부모의 검색 시작점

콴다·설탭은 TV·유튜브 광고 체급이고, 초기의 우리는 검색에서 이겨야 함. 학부모의 실제 경로는 네이버:

| 스마트플레이스 | 사업자 등록 후 즉시 등록 | 대면 서비스라 지도 노출 = 신뢰. "분당 과외" 지도 검색에 잡혀야 함 |

## 5. 🟠 후기 자산 루프 — 별점 논쟁을 데이터로 끝내기

- 현재 Testimonial DB 0행, 홈·리뷰 페이지 전부 하드코딩 fallback + 일괄 ★5 (`docs/PRODUCT_DESIGN_TRACKER.md` 디자인 §8 미결).
- 제품 안에 이미 루프 재료가 있음(수업 기록·리포트·인앱 알림). **제안**: 수업 4주차에 학부모에게 후기 요청(초기엔 매니저가 카카오로 수동) → 실명 일부+등급 변화+개별 별점으로 Testimonial DB 적재 → fallback 후기·하드코딩 별점을 실데이터로 교체. 파일럿 10명이면 8주 안에 진짜 후기 6~8개 확보 가능 — 이게 광고보다 전환에 크게 작용.

## 6. 🟠 콜드스타트 순서 — "증거 없이 광고 먼저"가 최대 낭비

현재 사이트는 골격(디자인·신뢰 장치)은 갖췄지만 증거(실제 강사·후기·사진·수치)가 빈 상태. 제안하는 출시 순서:

1. **주 0~2: 공급 먼저** — 강사 5~10명 확보 (대학 커뮤니티·지인, "창립 멤버" 조건: 수수료 우대/추천서). 강사 카드가 실물로 채워져야 학생 모집이 가능
2. **주 2~6: 파일럿 5~10가정** — 지인·맘카페 경유, 할인 조건 = 후기·사진 사용 동의. 이 기간에 상담 스크립트·매칭 SOP를 문서화
3. **주 6~10: 증거 전환** — 후기·Before/After·촬영 사진을 사이트에 반영, 수치를 실측치로 교체 (MK-6 해소)
4. **주 10~: 유료 채널** — §2 계측 위에서 네이버 검색광고부터 소액. CAC가 손익 맞는 채널만 증액
- 위 순서의 핵심: **1,200+/500+ 같은 주장 수치를 파일럿 이후 실측 소수치로 바꾸는 게 오히려 신뢰를 높임** ("첫 3개월, 12가정과 함께했습니다" — 설탭도 초기 기준시점 병기 방식 사용).

## 7. 🟡 상담 응답 SLA 운영화

- 사이트가 "당일~다음날 연락"을 약속함(FAQ) — 고액 상담 리드는 1시간 내 첫 터치가 전환율을 좌우함. 현재 알림이 인앱뿐이라 매니저가 신청을 놓치는 구조.
- **제안**: 상담 신청 → 매니저 휴대폰으로 즉시 알림(초기엔 무료 텔레그램/카카오워크 웹훅, 이후 SMS). 사이트 약속 문구를 "평균 응답 시간"으로 실측 후 업데이트. 놓친 리드 수를 주간 리뷰.

38. **P0** 신원 검증 표준화 — 범죄경력회보서(본인 발급) + 신분증 + 재학/졸업 증명을 필수 서류로 명문화, 체크리스트를 admin에 기록 (BR-6). "대표 직접 면접" 서사의 실체.
39. **P1** 매니저 플레이북 — 상담 스크립트·매칭 기준·리포트 검수 체크리스트 문서화. 2호 매니저 채용 전이라도 단일 실패점의 지식을 시스템으로 (BR-3).
40. **P1** 운영 반경 정의 — 파일럿 지역 행정동 단위로 확정, B-12 표기와 일치.
41. **P2** 선생님 온보딩 킷 — 30분 분량: 수업 표준, 숙제 등록법, 리포트 작성 예시 2건.
42. **P2** CS 표준 — 채널(카카오)·1차 응답 목표(영업시간 내 2시간)·에스컬레이션 경로 1페이지.

## F. 법무·보안 (43–50)

43. **P0** 교습 형태 법률 자문 1회 — 중개 vs 직영 구조 확정 및 신고 요건 확인. 사업 구조 전체에 영향하므로 가장 먼저.
44. **P0** 법정대리인 동의 플로우 — 가입/상담 신청 시 보호자 동의 체크+기록. 만 14세 미만 별도 처리.
45. **P1** `question-images` private 전환 — 버킷 private 설정 + DB의 public URL을 경로 저장으로 마이그레이션 + 조회 시 서명 URL(또는 인증 프록시 라우트) 발급. 서류 버킷은 이미 안전하므로 P0 아님 (점검 완료).
46. **P1** 권한·감사 최소 구현 — 개인정보 열람 로그 테이블 1개 + admin 작업 기록. 완벽한 RBAC보다 "기록이 남는다"가 먼저.
47. **P1** 로그인 보호 — 전화번호 로그인에 시도 횟수 제한 + 지수 백오프. Vercel Firewall 룰 병행 검토.
48. **P1** 약관·방침 법률 검토 — 43번 자문과 같은 세션에서 처리 (환불 조항 중점).
49. **P2** AI 고지 문구 — 답변 하단 "AI 생성 답변입니다. 선생님이 확인 후 보완합니다" 1줄 + 약관 면책 조항.
50. **P1** 시드 데이터 가드 — 프로덕션 노출 전 체크: 시드 계정 이메일 패턴(@test 등) 필터를 공개 쿼리에 상시 적용, 배포 전 스모크 체크리스트에 "가짜 데이터 노출" 항목 추가.
