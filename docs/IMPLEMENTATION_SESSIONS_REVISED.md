# 실제 구현 세션 실행 순서 — 사용자 운영 방침 반영본

> 작성: 2026-07-02
> 기준 문서: `PRE_LAUNCH_RISK_REVIEW.md`, `BUSINESS_AND_MARKETING_REVIEW.md`, `PRODUCT_IMPROVEMENTS.md`, `IMPLEMENTATION_PLAN_2026-07.md`, `FLOW_EDGE_CASES_AND_IMPROVEMENTS.md`
> 중요: 기존 문서의 일부 제안은 실제 운영 방침과 다르므로, 구현은 이 문서를 우선 기준으로 한다.

## 0. 이번 문서에서 반영한 운영 방침

### 0.1 약관/환불/개인정보 문서

- 이용약관, 개인정보처리방침, 환불 규정은 홈페이지 본문에 길게 넣지 않는다.
- 각 문서는 별도 문서/페이지로 제공한다.
- 홈페이지와 결제 화면에는 작은 고지와 링크만 노출한다.
- 실제 법률 문구는 추후 별도 제공 예정이므로, 이번 구현에서는 문구를 하드코딩하지 않는다.

구현 원칙:
- `/terms`, `/privacy`, `/refund` 페이지는 유지한다.
- 현재 “준비 중” 상태는 운영상 위험하므로, 추후 제공될 문구를 넣을 수 있는 구조만 준비한다.
- 체크아웃/가입 화면에는 “이용약관 및 개인정보 처리방침에 동의한 것으로 간주됩니다” 수준의 간단한 안내와 링크를 둔다.
- 긴 약관 동의 플로우, 버전별 약관 관리, 복잡한 전자서명 구조는 이번 범위에서 제외한다.

### 0.2 후기 수집

- 사용자가 프로그램 안에서 직접 후기/평점을 제출하는 플로우는 만들지 않는다.
- 후기는 대면 상담/운영 과정에서 별도로 수집한다.
- 따라서 `TutorReview` 작성 API, 학생 후기 요청 푸시, 수업 후 별점 모달은 구현하지 않는다.

구현 원칙:
- 공개 후기/마케팅 후기는 Admin 또는 CMS에서 수동 등록하는 방향으로 유지한다.
- 앱/웹에서 사용자에게 “후기 남기기”를 요구하지 않는다.
- `PRODUCT_IMPROVEMENTS.md`의 FI-2는 자동 수집이 아니라 “운영 수집 후 Admin 반영”으로 재해석한다.

### 0.3 매칭 수락/거절

- 학생은 배정된 선생님을 “수락”만 할 수 있다.
- 학생 거절, 재배정 요청, 매니저 취소 플로우는 이번 범위에서 구현하지 않는다.
- 재배정은 시스템 기능이 아니라 운영자가 별도 처리하는 예외 업무로 둔다.

구현 원칙:
- 학생 화면에는 수락 버튼만 둔다.
- `decline`, `reject`, `request another teacher` 류의 UI/API는 만들지 않는다.
- 기존 문서의 EC-1, EC-3 중 “수락 경로 완성”만 반영한다.
- 거절/재배정 관련 알림 타입, API, 상태는 이번 마이그레이션에서 제외한다.

### 0.4 학부모 동의/보호자 정보

- 보호자 동의를 시스템적으로 받는 복잡한 플로우는 만들지 않는다.
- 서비스 이용은 학부모 동의가 된 것으로 간주한다는 안내 문구를 둔다.
- 결제 이후 매니저에게 전달되는 정보에 부모님 전화번호를 적을 수 있게 하는 정도로 충분하다.

구현 원칙:
- 보호자 별도 인증, 보호자 SMS 동의, 전자서명은 제외한다.
- 학생 가입/결제 후 정보 전달 단계에 `parentPhone` 또는 `guardianPhone` 필드를 추가하는 정도로 제한한다.
- 초등/중등 학년 선택에 따라 강제 분기하는 복잡한 보호자 동의 UI는 만들지 않는다.

- FI-2 후기/평점 자동 수집은 제외한다.

  - Admin/CMS에서 후기 콘텐츠를 수동 등록한다.
  - 앱/웹 사용자에게 후기 작성 요구를 하지 않는다.

- `matchReason`은 여전히 유효하다. 학생이 수락할 때 설득력을 주기 때문이다.

### 1.4 `FLOW_EDGE_CASES_AND_IMPROVEMENTS.md`

## 2. 실제 구현 세션 순서

## Session 1 — 법률 문서 노출 구조와 운영 고지 정리

목표:
- 긴 법률 문서를 지금 작성하지 않고도, 추후 문구를 넣을 수 있는 안전한 구조를 만든다.
- 홈페이지/가입/결제에는 작은 고지와 링크만 둔다.

범위:
1. `/terms`, `/privacy`, `/refund` 페이지 구조 정리
2. 각 페이지가 추후 제공될 문구를 표시할 수 있게 구성
3. 가입/결제 화면에 작은 고지 추가
4. “학부모 동의가 된 것으로 간주” 안내 문구 추가
5. 부모님 전화번호 입력/전달 필드 추가 여부 검토 및 최소 구현

제외:
- 약관 전문 작성
- 보호자 SMS 인증
- 약관 버전 관리
- 전자서명
- 복잡한 미성년자 분기

검증:
- `/terms`, `/privacy`, `/refund`가 빈 페이지가 아니어야 한다.
- 가입/결제 화면에서 관련 링크가 보여야 한다.
- 결제 이후 매니저가 부모님 연락처를 볼 수 있어야 한다. 단, 필수 여부는 UX를 보고 결정한다.

---

## Session 2 — 결제 서버 검증과 결제 실패 복구

목표:
- 결제 없이 구독이 활성화되는 구조를 차단한다.
- 결제 후 서버 처리 실패 시 복구 가능하게 한다.

범위:
1. Toss 서버 confirm 구현
2. 웹 결제 완료 API에서 `paymentKey`, `orderId`, `amount` 검증
3. 모바일 결제 완료 API도 동일 검증 또는 웹 체크아웃 위임
4. `PaymentCompletion` 실패 상태 재시도 가능하게 수정
5. Admin에서 실패/처리중 결제 확인 가능하게 최소 API 또는 로그 확보

제외:
- 자동결제/빌링키
- 정산 시스템
- 환불 자동화

검증:
- 잘못된 금액으로 완료 요청 시 실패해야 한다.
- 빈 `orderId`나 임의 요청으로 구독이 활성화되면 안 된다.
- 실패한 결제 완료 처리를 같은 `orderId`로 재시도할 수 있어야 한다.

---

## Session 3 — 매칭 수락 플로우 최소 완성

목표:
- 매니저가 선생님을 배정하면 학생이 웹/앱에서 수락하고, 그 뒤에만 활성 매칭이 되게 한다.

범위:
1. `TeacherStudent`에 수락 대기 상태 도입
2. 신규 매칭 생성 시 `isActive: false`, `matchStatus: PENDING_STUDENT_ACCEPT`로 생성
3. 학생 수락 API 공용 로직 작성
4. 모바일 수락 경로 정리
5. 웹 수락 경로 추가
6. 수락 후 `isActive: true`, `matchStatus: ACTIVE`, `respondedAt` 기록
7. 선생님 알림은 학생 수락 후 발송되게 정리

제외:
- 학생 거절
- 재배정 요청
- 매니저 매칭 취소
- `DECLINED` 상태
- `declineReason`

검증:
- 수락 전 학생은 활성 대시보드로 넘어가면 안 된다.
- 수락 전 선생님 포털에 활성 학생으로 뜨면 안 된다.
- 학생이 수락하면 선생님 포털에 학생이 보여야 한다.
- 웹 가입자도 앱 없이 수락할 수 있어야 한다.

---

## Session 4 — 첫 수업 설정과 Journey 정합성

목표:
- 학생 수락 이후 선생님이 첫 수업일을 설정하고, 웹/앱 journey가 같은 상태를 보여주게 한다.

범위:
1. 첫 수업 설정 API가 active 매칭에서만 동작하게 제한
2. `Lesson.lessonType = FIRST` 추가 검토
3. 과거 첫 수업 기록이 덮어써지지 않게 보호
4. 서버의 journey 계산을 웹/앱 공통 소스로 정리
5. 모바일 `me` 응답에 journey stage 포함

제외:
- 전체 수업 스케줄러
- 보강/취소/이월 정책 자동화
- 수업 완료 자동 정산

검증:
- 수락 전 첫 수업 설정이 불가능해야 한다.
- 첫 수업 설정 후 학생 화면 상태가 바뀌어야 한다.
- 웹과 앱의 journey 표시가 서로 다르면 안 된다.

## Session 5 — 매니저 전달 정보와 상담 운영 UX

목표:
- 결제/신청 이후 매니저가 학생과 학부모 연락 정보를 보고 실제 상담을 진행할 수 있게 한다.

범위:
1. 부모님 전화번호 필드 추가 또는 기존 메모/전달 필드 활용
2. 상담/매니저 화면에서 부모님 연락처 표시
3. “학부모 동의 간주” 안내 문구 표시
4. 서비스 지역/상담 가능 지역 노출
5. 방문 희망 시간 만료/재요청은 필요 시 후순위로 문서화

제외:
- 보호자 인증
- 보호자 별도 계정
- 보호자 SMS 동의

검증:
- 매니저가 상담 전 학생/학부모 연락처를 확인할 수 있어야 한다.
- 학생/학부모에게 동의 간주 안내가 노출되어야 한다.

## Session 6 — 제품 가치 활성화 1차: 월간 리포트/학습 그래프

목표:
- 앱/웹에서 비어 있는 기능을 줄이고, 학부모가 서비스 가치를 체감하게 한다.

범위:
1. 월간 리포트 생성 로직 추가
2. 리포트 생성 크론 추가
3. 수업/과제 데이터를 기반으로 학습 그래프 표시
4. 가짜 추정치가 아니라 실제 기록만 사용

제외:
- 사용자 후기 자동 수집
- 학생 별점 제출
- 자동 마케팅 후기 전환

검증:
- 테스트 학생에게 리포트가 생성되어야 한다.
- 데이터가 없을 때 빈 상태가 자연스럽게 보여야 한다.
- 학습 그래프가 항상 0으로만 보이면 안 된다.

4. 미답변 QnA 감시 확장

제외:

- 자동 재결제

검증:

- 푸시/인앱 알림 타입이 깨지지 않아야 한다.
- 크론 주기 변경 시 기존 일일 체크가 과발송되지 않아야 한다.

3. 숙제 분배 시 기존 학생 계획 append 방식 적용

- 완료한 숙제 삭제

검증:
- 기존 학생 태스크가 삭제되면 안 된다.
- 완료한 태스크가 재분배로 사라지면 안 된다.
- 템플릿을 재사용할 수 있어야 한다.

## 5. Claude Code 세션 지시용 압축 순서

실제 Claude Code에 넘길 때는 아래 순서로 한 세션씩 진행한다.

1. `legal-notice-pages-and-parent-contact`
   - 법률 문서 페이지 구조, 작은 고지, 부모님 전화번호 전달

2. `toss-payment-confirm-and-retry`
   - Toss confirm, 금액 검증, 실패 결제 재시도

3. `student-accept-only-match-flow`
   - 학생 수락만 있는 매칭 플로우. 거절/재배정 금지

4. `first-lesson-and-journey-sync`
   - 첫 수업 설정 가드, journey 서버 단일화

5. `manager-consultation-operational-fields`
   - 매니저가 볼 연락처/상담 정보 정리

6. `monthly-report-and-learning-graph`
   - 리포트 생성, 학습 그래프 실데이터화

7. `reminders-and-alert-checks`
   - 수락 대기, 첫 수업 미설정, 수업 전, 만료, QnA 리마인더

8. `homework-template-append-distribution`
   - 숙제 템플릿, append 분배, 기존 계획 보존

## 6. 최종 판단

기존 docs의 방향은 전체 리스크를 넓게 잡는 데는 좋지만, 실제 구현은 운영 방침에 맞춰 더 단순해야 한다.

가장 중요한 변경은 다음 네 가지다.

1. 법률 문서는 별도 제공, 홈페이지에는 작은 고지와 링크만 둔다.
2. 후기는 프로그램에서 직접 수집하지 않는다.
3. 학생은 선생님을 거절하지 않고 수락만 한다.
4. 보호자 동의는 시스템적으로 받지 않고, 동의 간주 안내와 부모님 전화번호 전달로 제한한다.

따라서 앞으로 구현 계획은 이 문서를 우선 기준으로 삼고, 기존 문서들은 세부 근거 자료로만 참고한다.
